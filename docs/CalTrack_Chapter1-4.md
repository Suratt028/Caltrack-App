# CalTrack Documentation: บทที่ 1-4

## บทที่ 1: บทนำ

### 1.1 ภูมิหลังและปัญหา
การติดตามอาหารและพลังงานเป็นส่วนสำคัญของการดูแลสุขภาพ แต่ผู้ใช้หลายคนพบปัญหาในการจดบันทึกเมนูประจำวันและคำนวณปริมาณสารอาหารด้วยตัวเอง เมื่อไม่มีเครื่องมือช่วย การควบคุมน้ำหนักและการตั้งเป้าหมายโภชนาการจะทำได้ยากและไม่ต่อเนื่อง

ในบริบทของคนไทย ปัญหายิ่งซับซ้อนขึ้นเพราะเมนูอาหารไทยมีความหลากหลาย การแปลชื่ออาหารเป็นภาษาอังกฤษและการหาแคลอรี่ที่แม่นยำจึงเป็นเรื่องท้าทาย นอกจากนี้ ผู้ใช้ทั่วไปอาจไม่เข้าใจค่า BMR, TDEE และ macro goals อย่างชัดเจน

### 1.2 วัตถุประสงค์ของโครงการ
- สร้างแอปมือถือสำหรับติดตามแคลอรี่และสารอาหาร โดยเน้นการใช้งานง่ายสำหรับคนไทย
- ให้ผู้ใช้บันทึกอาหารทั้งมื้อต่าง ๆ ได้รวดเร็วและสะดวก
- แสดงผลสรุปพลังงานรายวันและกราฟเทรนด์ เพื่อช่วยให้ผู้ใช้เห็นภาพรวมสุขภาพได้อย่างชัดเจน
- คำนวณเป้าหมายพลังงานและสารอาหารตามข้อมูลร่างกายของผู้ใช้
- รองรับการใช้งานแบบ offline-first โดยมี fallback dataset เมื่อไม่เชื่อมต่อฐานข้อมูลภายนอก

### 1.3 ขอบเขตของโครงการ
- พัฒนาโดยใช้ React Native และ Expo เป็นหลัก
- รองรับฟังก์ชันหลัก ได้แก่
  - ลงทะเบียน / เข้าสู่ระบบ
  - Onboarding เพื่อกรอกข้อมูลร่างกายและเป้าหมาย
  - บันทึกอาหารด้วยการค้นหาจากฐานข้อมูลอาหาร
  - สแกนอาหารด้วย Gemini Vision AI เพื่อประเมินแคลอรี่และสารอาหารจากภาพ
  - แสดงกราฟเทรนด์แคลอรี่และน้ำหนัก
  - ปรับปรุงโปรไฟล์และเป้าหมายโภชนาการ
- มี backend แบบง่ายด้วย Express และ MongoDB เพื่อจัดเก็บข้อมูลผู้ใช้, โปรไฟล์, และบันทึกอาหาร
- ขอบเขตในเวอร์ชันนี้ยังไม่รวมระบบ auth token ขั้นสูง หรือการ sync ข้อมูลข้ามหลายอุปกรณ์อย่างสมบูรณ์

## บทที่ 2: แนวทางทฤษฎีและงานที่เกี่ยวข้อง

### 2.1 งานที่เกี่ยวข้อง
- **MyFitnessPal**: แอปเครื่องมือบันทึกอาหารที่มีฐานข้อมูลอาหารขนาดใหญ่และระบบคำนวณโภชนาการแบบอัตโนมัติ
- **NubCal / Kalguroo**: แอปสแกนอาหารด้วยภาพ ซึ่งประเมินพลังงานและสารอาหารจากภาพถ่ายอาหาร
- **แอปสุขภาพทั่วไป**: เช่น Google Fit, Apple Health ที่เน้นติดตามกิจกรรมและน้ำหนัก โดย CalTrack มุ่งเน้นด้านโภชนาการเป็นหลัก

แอปที่เกี่ยวข้องช่วยกำหนดแนวทางในการออกแบบ UI/UX, Flow การใช้แอป, และรูปแบบการแสดงผลสรุปให้ผู้ใช้เข้าใจได้ง่าย

### 2.2 สูตรคำนวณโภชนาการ
- **BMR (Basal Metabolic Rate)**
  - ใช้สูตร Mifflin-St Jeor ซึ่งเป็นสูตรที่สอดคล้องกับการศึกษาทางโภชนาการ
  - สูตรทั่วไป:
    - ชาย: BMR = 10 × น้ำหนัก (kg) + 6.25 × ส่วนสูง (cm) - 5 × อายุ + 5
    - หญิง: BMR = 10 × น้ำหนัก (kg) + 6.25 × ส่วนสูง (cm) - 5 × อายุ - 161
- **TDEE (Total Daily Energy Expenditure)**
  - คำนวณจาก BMR คูณด้วยปัจจัยกิจกรรม
  - ปัจจัยกิจกรรมในระบบ:
    - sedentary = 1.2
    - light = 1.375
    - moderate = 1.55
    - active = 1.725
    - very_active = 1.9
- **เป้าหมายแคลอรี่**
  - ลดน้ำหนัก: TDEE - 500 kcal
  - รักษาน้ำหนัก: TDEE
  - เพิ่มน้ำหนัก: TDEE + 300 kcal
  - แอปตั้งเพดานขั้นต่ำ 1200 kcal เพื่อความปลอดภัย
- **Macro split**
  - ปริมาณสารอาหารหลักคำนวณจากเป้าหมายแคลอรี่
  - สูตรที่ใช้:
    - โปรตีน 25% ของแคลอรี่
    - คาร์โบไฮเดรต 45% ของแคลอรี่
    - ไขมัน 30% ของแคลอรี่
  - แปลงเป็นกรัมด้วย:
    - โปรตีน 4 kcal ต่อกรัม
    - คาร์โบไฮเดรต 4 kcal ต่อกรัม
    - ไขมัน 9 kcal ต่อกรัม

### 2.3 เทคโนโลยีที่ใช้
- **Frontend**
  - React Native + Expo: ทำให้พัฒนาแอปบนมือถือได้รวดเร็วและรองรับทั้ง Android, iOS
  - React Navigation: จัดการการนำทางแบบ bottom-tab, stack
  - AsyncStorage: เก็บสถานะพื้นฐานของผู้ใช้และบันทึกในเครื่อง
  - react-native-svg: วาดกราฟและวงแหวนแคลอรี่โดยไม่ต้องพึ่ง library chart ขนาดใหญ่
- **Backend**
  - Node.js + Express: ให้ API พื้นฐานสำหรับ auth, โปรไฟล์, และบันทึก
  - MongoDB / Mongoose: เก็บข้อมูลผู้ใช้, โปรไฟล์, และ log entry
- **บริการเพิ่มเติม**
  - MongoDB Atlas Data API: ใช้ค้นหาข้อมูลอาหารจาก collection `foods` เมื่อมีการตั้งค่า
  - Google Gemini 1.5 Flash Vision API: วิเคราะห์ภาพอาหารและประมาณค่าแคลอรี่/สารอาหาร (เรียกผ่าน backend endpoint `/api/ai/scan`)
  - Fallback dataset: ให้แอปยังใช้งานได้แม้ไม่มีการเชื่อมต่อ Atlas หรือ Gemini API key

## บทที่ 3: การออกแบบระบบและการพัฒนา

### 3.1 สถาปัตยกรรมระบบ
ระบบแบ่งออกเป็น 3 ชั้นหลัก:
- **Presentation layer**: หน้าจอและคอมโพเนนต์ UI
- **State layer**: `AppContext` จัดการ state กลาง, persistence, และการเชื่อมต่อ backend
- **Data layer**: service modules สำหรับเรียก API และค้นหาข้อมูลอาหาร

Flow การใช้งานหลัก:
1. ผู้ใช้เปิดแอป
2. หากยังไม่ล็อกอินแสดง `AuthScreen`
3. หลังเข้าสู่ระบบแล้ว หากยังไม่กรอกโปรไฟล์ให้แสดง `OnboardingScreen`
4. เมื่อพร้อมแล้ว ผู้ใช้เข้าสู่หน้า `RootNavigator` ที่มี tab หลัก
5. ผู้ใช้สามารถบันทึกอาหาร, สแกนอาหาร, ดูเทรนด์, แก้ไขโปรไฟล์

### 3.2 โครงสร้างโมดูลหลัก
- **`App.js`**
  - จัดการ SafeAreaProvider และ AppProvider
  - ตัดสินใจว่าเมื่อใดจะโชว์ Auth, Onboarding, หรือ Tab Navigator
- **`AppContext.js`**
  - เก็บข้อมูลโปรไฟล์, บันทึกอาหาร, น้ำหนัก, user session
  - ทำงานกับ AsyncStorage และ backend API
  - มี logic สำหรับเรียก `fetchProfile` และ `fetchLogs` เมื่อ login
- **`foodService.js`**
  - ค้นหาข้อมูลอาหาร
  - ใช้ MongoDB Atlas Data API เมื่อ configured
  - มี fallback dataset local เพื่อให้แอปใช้งานได้ทันที
- **`atlasService.js`**
  - wrapper สำหรับ fetch API จาก backend
  - รองรับ auth, profile, log operations
- **`aiVisionService.js`**
  - วิเคราะห์ภาพอาหารผ่าน backend endpoint `/api/ai/scan`
  - มี fallback เป็นเมนูอาหารไทยตัวอย่างเมื่อ Gemini API ไม่พร้อมใช้งาน
- **หน้าจอหลัก**
  - `HomeScreen.js`: สรุปแคลอรี่, macro goals, และรายการอาหารวันนี้
  - `LogScreen.js`: ค้นหาอาหาร, เลือกมื้อ, ใส่จำนวนและบันทึก
  - `ScanScreen.js`: ถ่ายรูป/เลือกรูป → Gemini Vision วิเคราะห์ → แก้ไขผลลัพธ์ → บันทึกลงไดอารี่
  - `TrendsScreen.js`: แสดงกราฟแคลอรี่ 7 วันและแนวโน้มน้ำหนัก
  - `ProfileScreen.js`: แก้ไขข้อมูลส่วนตัว, ระดับกิจกรรม, และเป้าหมาย

### 3.3 การออกแบบฐานข้อมูล
- **`users` collection**
  - `_id`, `email`, `password`, `displayName`, `createdAt`
  - ใช้ hash password ด้วย HMAC-SHA256 ใน backend
- **`profiles` collection**
  - `userId`, `gender`, `age`, `heightCm`, `weightKg`, `activityLevel`, `goal`, `targetWeightKg`, `kcalGoal`, `proteinGoal`, `carbsGoal`, `fatGoal`, `updatedAt`
- **`logs` collection**
  - `userId`, `dateKey`, `entry`, `createdAt`
  - `entry` เป็น object เก็บข้อมูลอาหารแต่ละรายการสำหรับวันนั้น

### 3.4 การออกแบบ UI/UX
- ใช้โทนสีอ่อนและอ่านง่าย เพื่อให้แอปดูเรียบร้อยสำหรับผู้ใช้ทั่วไป
- UI มีปุ่มหลักและปุ่ม outline เพื่อแยก action สำคัญ
- ให้ผู้ใช้เข้าสู่ระบบง่าย และมีทางเลือกกลับไป `signup`/`login`
- หน้าจอ `Home` แสดงวงแหวนแคลอรี่และเป้าหมาย macro อย่างชัดเจน
- `LogScreen` ใช้ระบบค้นหา + modal preview เพื่อให้การบันทึกอาหารสมูท
- `ScanScreen` ให้ผู้ใช้ปรับแก้ค่าผลลัพธ์จาก AI ก่อนบันทึก และแสดง tag แยกระหว่างผลจาก Vision AI กับโหมด Demo
- `TrendsScreen` แสดงข้อมูลในรูปกราฟแท่งและเส้น ช่วยให้ผู้ใช้เห็นแนวโน้มได้ง่าย

## บทที่ 4: การทดสอบและผลลัพธ์

### 4.1 วิธีการทดสอบ
- **Functional testing**
  - ทดสอบสมัครสมาชิก, เข้าสู่ระบบ, logout
  - ทดสอบ onboarding flow และการกรอกข้อมูลร่างกาย
  - ทดสอบการบันทึกอาหารผ่าน `LogScreen`
- **AI Vision testing**
  - ตั้งค่า `GEMINI_API_KEY` ใน `.env` ของ backend
  - รัน backend ด้วย `npm run server`
  - ทดสอบ `POST /api/ai/scan` ด้วยภาพอาหาร base64
  - ทดสอบ `ScanScreen` บนมือถือ: ถ่ายรูป → ตรวจสอบผลลัพธ์ → แก้ไข → บันทึก
  - ทดสอบ fallback เมื่อไม่มี API key (ควรได้เมนูตัวอย่างและ source เป็น `fallback_no_key`)
- **Integration testing**
  - ทดสอบการเชื่อมต่อ backend API ผ่าน `atlasService`
  - ตรวจสอบการเรียก `fetchProfile` / `fetchLogs` หลัง login
- **UI testing**
  - ทดสอบการเรนเดอร์ `HomeScreen`, `TrendsScreen`, `ProfileScreen`
  - ตรวจสอบการแสดงผลข้อความ empty state, error state
- **Edge case testing**
  - ทดสอบ fallback เมื่อ MongoDB Atlas Data API ไม่พร้อมใช้งาน
  - ทดสอบ fallback เมื่อ Gemini API ล้มเหลวหรือไม่มี key
  - ทดสอบการป้อนค่าไม่ถูกต้องใน input
  - ทดสอบช่องว่างและการกดปุ่มกลับ

### 4.2 ผลลัพธ์ที่ได้
- ผู้ใช้งานสามารถลงทะเบียนและเข้าสู่ระบบได้
- ระบบสามารถคำนวณ BMR, TDEE, และเป้าหมายแคลอรี่ได้ตามข้อมูลผู้ใช้
- `HomeScreen` แสดงยอดพลังงานที่บริโภคและเป้าหมายรายวัน
- `LogScreen` ค้นหาและบันทึกอาหารได้อย่างรวดเร็ว พร้อมแสดง macro value
- `ScanScreen` วิเคราะห์ภาพอาหารด้วย Gemini Vision AI (เมื่อมี API key) และให้ผู้ใช้แก้ไขก่อนบันทึก
- backend endpoint `/api/ai/scan` ตอบกลับ JSON ที่มีชื่อเมนู, แคลอรี่, macro และค่า confidence
- `TrendsScreen` แสดงกราฟแคลอรี่และแนวโน้มน้ำหนักสำหรับผู้ใช้ที่บันทึกข้อมูล

### 4.3 ข้อจำกัดปัจจุบัน
- ค่าแคลอรี่จาก AI เป็นการประมาณการ ไม่ได้อ้างอิงฐานข้อมูลอาหารไทยอย่างเป็นทางการ
- ต้องมี `GEMINI_API_KEY` ใน backend จึงจะได้ผลลัพธ์จาก Vision AI จริง หากไม่มีจะ fallback เป็นเมนูตัวอย่าง
- ข้อมูลอาหารยังไม่ครบทุกเมนู และยังพึ่งพา fallback dataset ในบางกรณี
- ระบบ auth ยังยึดค่า session แบบ local แต่ไม่มี token-based authentication ระดับสูง
- การซิงค์ข้อมูลข้ามอุปกรณ์ยังไม่สมบูรณ์หากผู้ใช้เปลี่ยนอุปกรณ์โดยไม่มี cloud sync ที่ครอบคลุม

### 4.4 แนวทางพัฒนาต่อ
- **เชื่อมต่อฐานข้อมูลอาหารจริง**
  - สร้าง collection อาหารที่ครอบคลุมเมนูไทยและสากล
  - ปรับ `foodService` ให้ใช้งาน Atlas Data API หรือ API ภายนอกได้อย่างมั่นคง
- **ปรับปรุงความแม่นยำของ AI Vision**
  - cross-check ผลลัพธ์จาก Gemini กับฐานข้อมูลอาหารในระบบ
  - เก็บ feedback เมื่อผู้ใช้แก้ไขผลลัพธ์ เพื่อปรับ prompt หรือ fine-tune
- **เพิ่มการจัดการ session**
  - ใช้ token-based auth หรือ OAuth
  - เพิ่ม refresh token และ expiry handling ใน backend
- **ขยายฟีเจอร์ sync**
  - ซิงค์บันทึกและโปรไฟล์ข้ามอุปกรณ์ผ่าน cloud
  - เพิ่มระบบ backup/restore
- **ปรับ UI/UX**
  - รองรับ dark mode
  - เพิ่ม accessibility สำหรับผู้มีปัญหาทางสายตา
  - ขยายการรองรับหลายภาษา
