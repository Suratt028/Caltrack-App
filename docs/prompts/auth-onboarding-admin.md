# Prompt: ปรับปรุงหน้าเข้าสู่ระบบ หน้าเริ่มต้นใช้งาน และหน้าผู้ดูแลระบบของ CalTrack

## บทบาท
คุณคือ Senior Full-Stack Engineer และ UX Engineer ที่เชี่ยวชาญ React Native (Expo), React Native Web, Node.js/Express และ MongoDB งานของคุณคือปรับปรุงสามส่วนของแอป CalTrack ให้พร้อมใช้งานจริง (production-ready): (1) หน้าเข้าสู่ระบบ/สมัครสมาชิก `src/screens/AuthScreen.js` (2) หน้าเริ่มต้นใช้งาน `src/screens/OnboardingScreen.js` และ (3) หน้าเว็บผู้ดูแลระบบ `src/screens/Admin/AdminScreen.js` พร้อมหน้าย่อยใน `src/components/admin/`

## บริบทของโปรเจกต์
- CalTrack เป็นแอปนับแคลอรี่และติดตามโภชนาการภาษาไทย ทำงานบน Android, iOS และ Expo Web จาก codebase เดียว
- Stack: React Native 0.86, Expo 57, React 19, React Navigation 7, AsyncStorage, react-native-svg (ไม่มี chart library), backend เป็น Express + Mongoose ใน `server.js` และ helper ใน `server/`
- State กลางอยู่ใน `src/context/AppContext.js` การเรียก API อยู่ใน `src/services/atlasService.js` และ URL อยู่ใน `src/config.js`
- Flow ปัจจุบัน: `App.js` โหลด state จาก AsyncStorage → ไม่มี user แสดง `AuthScreen` → login แล้วแต่ไม่มี profile แสดง `OnboardingScreen` → เสร็จแล้วเข้า `RootNavigator` (Home, Log, Scan, Trends, Profile)
- Design tokens อยู่ใน `src/theme/colors.js` (โทน "leaf": `primary #21634C`, `primaryDark #1B3D2F`, `bg #F7F5F0`, `surface #FFFFFF`, `ink #1F3A2F`, `inkMuted #5F6F67`, `turmeric #B5832E`, `danger #B23E28` ซึ่งใช้กับ error จริงเท่านั้น) และฟอนต์ Noto Sans Thai ผ่าน `AppText` / `AppTextInput` ใน `src/theme/fonts.js`
- Styles แยกไฟล์ไว้ใน `src/style/screens/*Styles.js` ให้ใช้รูปแบบนี้ต่อ ห้ามเขียน inline style ยาว ๆ ใน component
- Component ที่มีอยู่แล้วและควรนำกลับมาใช้: `PrimaryButton`, `Card`, `Banner`, `ScreenHeader`, `SegmentedControl`, `GoalPresetButton`, `EmptyState`, `OfflineState`, `TrendBarChart`, `TrendDataTable`, `TrendStatCard` และ `confirmAsync` จาก `src/utils/confirm.js`

## ข้อกำหนดร่วมทั้งสามหน้า
1. **อ่านโค้ดเดิมก่อนแก้** ทำความเข้าใจ state, service และ API contract ที่มีอยู่ อย่าเปลี่ยน endpoint หรือรูปแบบ response โดยไม่จำเป็น หากต้องเปลี่ยน ให้แก้ทั้งฝั่ง client, server และ test พร้อมกัน แล้วอธิบายเหตุผล
2. **ภาษาไทยเป็นหลัก** ข้อความทุกจุดต้องเป็นภาษาไทยที่เป็นธรรมชาติ สุภาพ กระชับ ไม่แปลตรงตัวจากภาษาอังกฤษ ตัวเลขและหน่วยใช้รูปแบบไทย (เช่น `1,850 kcal`, `กก.`, `ซม.`)
3. **Accessibility (WCAG 2.1 AA)** contrast ข้อความอย่างน้อย 4.5:1 ใช้ token เดิมที่ผ่านแล้ว พื้นที่แตะอย่างน้อย 44×44 pt ทุกปุ่มและช่องกรอกมี `accessibilityLabel`, `accessibilityRole` และ `accessibilityState` ที่ถูกต้อง error message ต้องผูกกับช่องกรอกและอ่านได้ด้วย screen reader (`accessibilityLiveRegion="polite"` บน Android) ห้ามใช้สีเพียงอย่างเดียวสื่อความหมาย
4. **Responsive** มือถือ 360 px ถึงเดสก์ท็อป 1440 px ฝั่งเว็บต้องจำกัดความกว้างเนื้อหา (เช่น auth card ไม่เกิน 440 px) ไม่มี horizontal scroll รองรับ safe area และคีย์บอร์ด (`KeyboardAvoidingView` + `ScrollView` พร้อม `keyboardShouldPersistTaps="handled"`)
5. **สถานะครบทุกแบบ** ทุกการเรียก API ต้องมี loading, success, error, empty และ offline ปุ่ม submit ต้อง disable ระหว่างส่งเพื่อกันกดซ้ำ ใช้ `AbortController` หรือ flag เพื่อป้องกัน setState หลัง component unmount
6. **ความปลอดภัย** ห้าม hardcode secret, API key หรือรหัสผ่าน ห้ามใช้ prefix `EXPO_PUBLIC_` กับค่าลับ ห้าม log token หรือรหัสผ่าน error ที่แสดงต่อผู้ใช้ต้องไม่เปิดเผยรายละเอียดภายใน (stack trace, ชื่อ collection) ข้อความ login ล้มเหลวต้องเป็นแบบกลาง ๆ ("อีเมลหรือรหัสผ่านไม่ถูกต้อง") เพื่อกัน user enumeration
7. **โค้ดคุณภาพ** แยก logic ที่เป็น pure function (validation, การคำนวณ, การ map error) ออกไปไว้ใน `src/utils/` เพื่อให้เขียน unit test ได้ ใช้ชื่อตัวแปรสื่อความหมาย ไม่มี `TODO` หรือโค้ดค้างครึ่งทาง

## หน้าที่ 1: หน้าเข้าสู่ระบบและสมัครสมาชิก (AuthScreen)

### เป้าหมาย
ให้ผู้ใช้เข้าสู่ระบบหรือสมัครได้ภายใน 30 วินาที รู้สึกมั่นใจและปลอดภัย และใช้หน้าจอเดียวกันทั้งมือถือและเว็บ

### โครงสร้างหน้าจอ
- ส่วนหัว: โลโก้จาก `assets/logo.svg` ชื่อ "CalTrack" และ tagline สั้น ๆ เช่น "บันทึกอาหารไทย รู้แคลอรี่ได้ทันที"
- `SegmentedControl` สลับ "เข้าสู่ระบบ" / "สมัครสมาชิก" โดยคงค่าอีเมลที่กรอกไว้เมื่อสลับโหมด
- ช่องกรอก:
  - **อีเมล**: `keyboardType="email-address"`, `autoCapitalize="none"`, `autoComplete="email"`, `textContentType="emailAddress"` ตัดช่องว่างและแปลงเป็นตัวพิมพ์เล็กก่อนส่ง
  - **รหัสผ่าน**: ปุ่มแสดง/ซ่อนรหัสผ่านพร้อม label ที่เปลี่ยนตามสถานะ `textContentType` เป็น `password` หรือ `newPassword` ตามโหมด
  - **โหมดสมัคร**: เพิ่มชื่อที่แสดง และยืนยันรหัสผ่าน พร้อมตัวบอกความแข็งแรงของรหัสผ่าน (อย่างน้อย 8 ตัวอักษร มีตัวอักษรและตัวเลข) ที่บอกเป็นข้อความ ไม่ใช่สีอย่างเดียว
- ลิงก์ "ลืมรหัสผ่าน?" ไปยังโหมด `forgot` ซึ่งมีสองขั้นตามโค้ดเดิม: กรอกอีเมลเพื่อขอรหัส แล้วกรอกรหัสยืนยัน 6 หลักพร้อมรหัสผ่านใหม่ ขั้นที่สองต้องมีปุ่ม "ส่งรหัสอีกครั้ง" พร้อม cooldown 60 วินาทีแสดงเวลานับถอยหลัง และข้อความหลังขอรหัสต้องเป็นแบบกลาง ("หากอีเมลนี้มีบัญชี เราได้ส่งรหัสไปแล้ว")
- เส้นแบ่ง "หรือ" ตามด้วยปุ่ม Google และ Apple ตามแนวทางแบรนด์ของแต่ละเจ้า แสดงปุ่ม Apple เฉพาะเมื่อ `AppleAuthentication.isAvailableAsync()` เป็นจริงบน iOS หรือเมื่อตั้งค่า Apple web flow ไว้แล้ว ซ่อนปุ่มที่ยังไม่ได้ตั้งค่า client ID แทนการแสดงปุ่มที่กดแล้วพัง
- ท้ายหน้า: ข้อความยอมรับเงื่อนไขและนโยบายความเป็นส่วนตัวในโหมดสมัคร

### พฤติกรรมและ validation
- validate แบบ on-blur และตอนกด submit ไม่ขึ้น error ขณะผู้ใช้ยังพิมพ์ไม่เสร็จ (ใช้ state `touched` แบบเดียวกับ Onboarding)
- กด Enter / ปุ่ม Next บนคีย์บอร์ดเพื่อเลื่อนไปช่องถัดไปและ submit ในช่องสุดท้าย
- map error จาก backend เป็นข้อความไทยในฟังก์ชันเดียว (ต่อยอดจาก mapper ที่มีอยู่ในไฟล์) ครอบคลุม: เครือข่ายขัดข้อง, เซิร์ฟเวอร์ไม่ตอบ, HTTP 429 จาก rate limit (บอกให้รอสักครู่ แสดงเวลาถ้า header `Retry-After` มี), อีเมลถูกใช้แล้ว, รหัสยืนยันผิดหรือหมดอายุ, ระบบส่งอีเมลยังไม่ได้ตั้งค่า
- ถ้า backend ไม่พร้อม ให้แสดง `Banner` เตือนที่ด้านบนพร้อมปุ่ม "ลองอีกครั้ง" ที่เรียก `/api/health`
- บัญชีแอดมินที่ login ผ่านหน้านี้จะได้ admin token ตามที่ AppContext จัดการอยู่ ต้องคงพฤติกรรมนี้ไว้และนำทางไปหน้า Admin อย่างถูกต้อง

### สิ่งที่ต้องระวัง
- เก็บ token ผ่าน AppContext เท่านั้น บน native ให้พิจารณาย้าย token ไปเก็บใน `expo-secure-store` แทน AsyncStorage และอธิบาย migration สำหรับผู้ใช้เดิม
- ล้าง state รหัสผ่านทุกครั้งที่สลับโหมดหรือ login สำเร็จ

## หน้าที่ 2: หน้าเริ่มต้นใช้งาน (OnboardingScreen)

### เป้าหมาย
เก็บข้อมูลที่จำเป็นต่อการคำนวณเป้าหมายแคลอรี่ให้ครบ ด้วยขั้นตอนที่สั้น เข้าใจง่าย และให้ผู้ใช้เห็นคุณค่าก่อนเข้าแอป

### ขั้นตอน (คงโครง 4 ขั้นเดิม และเพิ่มหน้าสรุป)
1. **เพศ**: การ์ดเลือก ชาย / หญิง พร้อมคำอธิบายสั้นว่าใช้คำนวณ BMR
2. **ข้อมูลร่างกาย**: อายุ (13–100 ปี), ส่วนสูง (100–250 ซม.), น้ำหนัก (30–300 กก.) รับทศนิยม 1 ตำแหน่งสำหรับน้ำหนัก รองรับทั้งจุดและจุลภาคเป็นตัวคั่นทศนิยม แสดง error ใต้ช่องเมื่อนอกช่วง ใช้ `keyboardType="decimal-pad"`
3. **ระดับกิจกรรม**: 5 ตัวเลือกตาม activity factor `1.2`, `1.375`, `1.55`, `1.725`, `1.9` แต่ละตัวมีชื่อและตัวอย่างชีวิตประจำวันที่คนไทยเข้าใจ เช่น "ทำงานออฟฟิศ แทบไม่ได้ออกกำลังกาย"
4. **เป้าหมาย**: ลดน้ำหนัก (TDEE − 500), รักษาน้ำหนัก (TDEE), เพิ่มน้ำหนัก (TDEE + 300) ใช้ `GoalPresetButton`
5. **หน้าสรุป (ใหม่)**: แสดง BMR, TDEE, เป้าหมายแคลอรี่รายวัน และ macro (โปรตีน 25%, คาร์โบไฮเดรต 45%, ไขมัน 30%) เป็นกรัม พร้อมแหวนแคลอรี่จาก `CalorieRing` และอธิบายสั้น ๆ ว่าตัวเลขมาจากสูตร Mifflin-St Jeor หากเป้าหมายต่ำกว่า 1,200 kcal ให้ใช้ 1,200 และแจ้งผู้ใช้อย่างนุ่มนวลด้วยโทน turmeric ไม่ใช่สีแดง มีปุ่ม "แก้ไขข้อมูล" ที่ย้อนกลับไปขั้นที่ต้องการได้ และปุ่ม "เริ่มใช้งาน"

### พฤติกรรม
- แถบความคืบหน้าด้านบนพร้อมข้อความ "ขั้นที่ X จาก Y · ชื่อขั้น" และอ่านได้ด้วย screen reader
- ปุ่ม "ถัดไป" disable จนกว่าขั้นนั้นจะถูกต้อง และมี hint บอกว่ายังขาดอะไร
- ปุ่มย้อนกลับ รวมถึงปุ่ม back ของ Android (`BackHandler`) ต้องย้อนขั้น ไม่ใช่ปิดแอป
- เก็บ draft ระหว่างทางลง AsyncStorage เพื่อให้ผู้ใช้ที่ปิดแอปกลางคันกลับมาทำต่อได้ ล้าง draft เมื่อบันทึก profile สำเร็จ
- การคำนวณทั้งหมดต้องเรียกจาก `src/utils/calculations.js` ห้ามคำนวณซ้ำใน component
- ตอนกด "เริ่มใช้งาน": บันทึก profile ผ่าน AppContext ซึ่ง sync ไป `PUT /api/profiles/:userId` หาก sync ล้มเหลวแต่บันทึกในเครื่องสำเร็จ ให้เข้าแอปได้และแจ้งว่าจะ sync ภายหลัง หากล้มเหลวทั้งหมดให้แสดง `submitError` พร้อมปุ่มลองอีกครั้ง
- ใส่หมายเหตุว่าตัวเลขเป็นค่าประมาณ ไม่ใช่คำแนะนำทางการแพทย์

## หน้าที่ 3: หน้าเว็บผู้ดูแลระบบ (AdminScreen)

### เป้าหมาย
ให้ผู้ดูแลจัดการผู้ใช้ ฐานข้อมูลอาหาร การตั้งค่า AI และ ticket ช่วยเหลือได้อย่างรวดเร็ว ปลอดภัย และตรวจสอบย้อนหลังได้ ออกแบบเพื่อเดสก์ท็อปเป็นหลักแต่ใช้บนแท็บเล็ตได้

### Layout
- เดสก์ท็อป (≥ 1024 px): sidebar ซ้ายกว้าง 240 px พื้น `primaryDark` ตัวอักษรขาว เมนูที่เลือกอยู่มีพื้นหลังและแถบด้านซ้ายชัดเจน ด้านบนเป็น top bar แสดงชื่อแอดมิน เวลาหมดอายุ session และปุ่มออกจากระบบ
- หน้าจอเล็ก: sidebar ยุบเป็น drawer หรือแถบเมนูแนวนอนที่ scroll ได้
- พื้นที่เนื้อหาจำกัดความกว้างไม่เกิน 1280 px

### เมนูและฟีเจอร์ (อิง endpoint ที่มีอยู่)
1. **ภาพรวม** (`GET /api/admin/overview`): การ์ดสถิติ จำนวนผู้ใช้ทั้งหมด, ผู้ใช้ใหม่ 7 วัน, ผู้ใช้ที่ active วันนี้, จำนวนการบันทึกอาหารวันนี้, จำนวนสแกน AI วันนี้และอัตราความสำเร็จ, ticket ที่ยังเปิด พร้อมกราฟแท่ง 7–30 วันด้วย `TrendBarChart` ใช้ timezone จาก `REPORT_TIMEZONE`
2. **ผู้ใช้** (`/api/admin/users`): ตารางพร้อมค้นหาแบบ debounce 300 ms, แบ่งหน้า, เรียงลำดับ คอลัมน์ ชื่อ อีเมล วิธีสมัคร (อีเมล/Google/Apple) วันที่สมัคร ใช้งานล่าสุด สถานะ ดูรายละเอียดและ food log ของผู้ใช้ (`/users/:userId/logs`) แก้ไข ระงับ หรือลบผู้ใช้ การลบต้องผ่าน `confirmAsync` ที่ให้พิมพ์อีเมลผู้ใช้เพื่อยืนยัน
3. **ฐานข้อมูลอาหาร** (`/api/admin/foods`): ตาราง ค้นหา เพิ่ม แก้ไข ลบ ฟอร์มมีชื่อไทย ชื่ออังกฤษ หมวด และสารอาหารต่อ 100 กรัม (kcal, โปรตีน, คาร์บ, ไขมัน) validate ว่าค่าไม่ติดลบ และเตือนเมื่อพลังงานจาก macro (4/4/9) ต่างจาก kcal ที่กรอกเกิน 15%
4. **AI Scan** (`/api/admin/ai-scan-config`, `/api/admin/scan-logs`): ตั้งโควตาสแกนต่อผู้ใช้ต่อวัน ลำดับ model fallback และเปิด/ปิดการเก็บรูป ดู log การสแกนพร้อมสถานะและเวลาตอบสนอง แสดงรูปเฉพาะเมื่อผู้ใช้ยินยอมเก็บรูป
5. **รายงานและส่งออก** (`/api/admin/reports`, `/export/user-foods.csv`, `/export/foods.json`): เลือกช่วงวันที่ ดาวน์โหลดไฟล์ผ่านการเรียกแบบมี Authorization header แล้วสร้าง Blob ไม่ใช่ใส่ token ใน URL ป้องกัน CSV injection โดย escape ค่าที่ขึ้นต้นด้วย `=`, `+`, `-`, `@` ฝั่ง server
6. **ช่วยเหลือ** (`/api/tickets`): รายการ ticket กรองตามสถานะ เปลี่ยนสถานะ ตอบกลับ และลบ
7. **ตั้งค่าระบบ** (`/api/admin/system-settings`): ฟอร์มพร้อมปุ่มบันทึกที่ active เมื่อมีการเปลี่ยนแปลงเท่านั้น และเตือนเมื่อออกจากหน้าโดยยังไม่บันทึก

### ความปลอดภัยฝั่งแอดมิน
- ทุก route `/api/admin/*` ต้องตรวจ admin token ฝั่ง server เสมอ การซ่อนเมนูฝั่ง client ไม่ใช่การป้องกัน
- admin token อายุ 8 ชั่วโมง เมื่อได้ 401 ให้ล้าง session และกลับหน้า login พร้อมข้อความ "เซสชันหมดอายุ กรุณาเข้าสู่ระบบอีกครั้ง" และเตือนล่วงหน้า 5 นาทีก่อนหมดอายุ
- บน Expo Web ที่ AsyncStorage คือ localStorage ซึ่งเสี่ยงต่อ XSS ให้เสนอทางเลือก เช่น เก็บ admin token ใน memory อย่างเดียว หรือย้ายไปใช้ httpOnly + SameSite=Strict cookie พร้อม CSRF protection อธิบาย trade-off แล้วเลือกแนวทางหนึ่ง
- บันทึก audit log ฝั่ง server ทุกการแก้ไข ลบ และเปลี่ยนการตั้งค่า (ใคร ทำอะไร กับอะไร เมื่อไร)
- ใช้ projection ใน Mongoose เพื่อไม่ส่ง `passwordHash`, reset code หรือ token ออกมาใน response ใด ๆ และ escape regex ในคำค้นหา
- แสดงอีเมลผู้ใช้แบบ mask ในตาราง (เช่น `som***@gmail.com`) และให้ดูเต็มเฉพาะหน้ารายละเอียด

### ประสิทธิภาพ
- แบ่งหน้าฝั่ง server ด้วย `limit` และ cursor หรือ `skip` ที่มีเพดาน ไม่โหลดผู้ใช้ทั้งหมดมาครั้งเดียว
- ตรวจว่ามี index สำหรับ field ที่ค้นหาและเรียง (`email`, `createdAt`, ชื่ออาหาร) หลีกเลี่ยง N+1 query ในหน้าภาพรวมด้วย aggregation pipeline
- เมื่อสลับเมนู ให้ยกเลิก request เก่าด้วย `AbortController` เพื่อกันข้อมูลซ้อน
- `AdminScreen.js` ปัจจุบันยาว 865 บรรทัด ให้แยกหน้าผู้ใช้และหน้าอาหารออกเป็น component ใน `src/components/admin/` และย้าย data fetching ไปเป็น custom hook

## การทดสอบ
ใช้ `node --test` ตามที่โปรเจกต์ใช้อยู่ใน `tests/` และ `mongodb-memory-server` สำหรับ test ฝั่ง API อย่างน้อยต้องมี:
- validation อีเมล รหัสผ่าน และข้อมูลร่างกาย รวมค่าขอบ (อายุ 12/13/100/101, น้ำหนัก "65,5")
- การคำนวณ BMR/TDEE/เป้าหมาย/macro และ calorie floor 1,200
- error mapper คืนข้อความไทยถูกต้องสำหรับ 400, 401, 409, 429, 500 และ network error
- API แอดมิน: ไม่มี token ได้ 401, user token ได้ 403, admin token ได้ 200, response ไม่มี `passwordHash`, คำค้นที่มีอักขระ regex ไม่ทำให้ query พัง
- CSV export escape ค่าที่เสี่ยง formula injection

## เกณฑ์การยอมรับ
- `npm test` ผ่านทั้งหมด และ `npx expo start --web` เปิดทั้งสามหน้าได้โดยไม่มี warning ใน console
- ใช้งานด้วยคีย์บอร์ดอย่างเดียวบนเว็บได้ครบ (Tab, Enter, Esc ปิด modal) และมี focus ring ที่มองเห็น
- ไม่มี secret ใหม่ใน repository และ `.env.example` อัปเดตหากเพิ่มตัวแปร
- README ส่วน Flow และ Backend API อัปเดตตามการเปลี่ยนแปลง

## รูปแบบคำตอบที่ต้องการ
1. สรุปแนวทางออกแบบและ trade-off 3–5 ข้อก่อนเขียนโค้ด
2. รายการไฟล์ที่สร้างหรือแก้ไข พร้อมเหตุผลสั้น ๆ
3. โค้ดเต็มของแต่ละไฟล์ (ไม่ตัดทอน)
4. test ที่เพิ่ม และวิธีรัน
5. ความเสี่ยงหรือสิ่งที่ยังต้องตัดสินใจ เช่น การย้าย token storage ซึ่งกระทบผู้ใช้เดิม
